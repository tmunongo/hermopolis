02.01

From Geometric Data to Pixels

A game scene is described geometrically: characters as meshes of triangles, positions as coordinates, surfaces as mathematical relationships. None of this is directly displayable. The rendering pipeline is the process that converts this abstract geometric description into a concrete grid of pixel colors.

At the end of every pipeline, the answer to the same question is written into the framebuffer: what color should this pixel be? Everything before that is preparation.

The pipeline is one-directional — data flows forward, one stage at a time. Each stage consumes the output of the previous one. This strict ordering is what allows GPUs to process many primitives simultaneously without conflict.

02.02

Triangles as the Universal Primitive

All rendering hardware works with triangles. Not squares, not circles, not arbitrary polygons — specifically triangles. This is not arbitrary. A triangle is the simplest polygon that defines a surface: any three non-collinear points define a unique plane, and the interior of the triangle is always flat and always convex.

Any polygon can be decomposed into triangles (tessellation). Any curve can be approximated by a sequence of small triangles. This universality means hardware only needs to solve one problem — and it can solve it extremely fast.

Why Not Quads?
A quadrilateral requires four vertices. If those four points are not coplanar (common in 3D), the "quad" has no well-defined surface — two of its possible triangulations produce different planes. Triangles never have this ambiguity. GPUs convert quads to triangles internally anyway.

02.03

The Rasterization Algorithm

Rasterization answers the question: which pixels does this triangle cover? The standard approach — the same one your GPU uses — is the edge function test. For each candidate pixel, three tests determine whether the pixel center falls inside the triangle.

Given a triangle edge from vertex A to vertex B, the edge function at point P is:

def edge(ax, ay, bx, by, px, py):
    # Signed area of the parallelogram formed by (A→B) and (A→P).
    # Positive if P is to the left of A→B (counter-clockwise winding).
    return (bx - ax) * (py - ay) - (by - ay) * (px - ax)python

A pixel is inside the triangle if all three edge functions return the same sign. For counter-clockwise vertex ordering, all three must be ≥ 0. 

def rasterize_triangle(v0, v1, v2, framebuffer, color):
    # Bounding box — only test pixels that could possibly be inside
    min_x = max(0, int(min(v0[0], v1[0], v2[0])))
    max_x = min(WIDTH-1, int(max(v0[0], v1[0], v2[0])))
    min_y = max(0, int(min(v0[1], v1[1], v2[1])))
    max_y = min(HEIGHT-1, int(max(v0[1], v1[1], v2[1])))

    for y in range(min_y, max_y + 1):
        for x in range(min_x, max_x + 1):
            # Test pixel center (x+0.5, y+0.5) against all three edges
            e0 = edge(*v0, *v1, x+0.5, y+0.5)
            e1 = edge(*v1, *v2, x+0.5, y+0.5)
            e2 = edge(*v2, *v0, x+0.5, y+0.5)
            if e0 >= 0 and e1 >= 0 and e2 >= 0:
                framebuffer[y, x] = colorpython
Pixel Centers
The test uses x+0.5, y+0.5 rather than x, y. Each pixel represents a unit-sized region of the screen; the center of that region is the canonical sample point. This is not optional — it determines exactly which pixels a triangle's edges claim.

The efficiency insight: a thin diagonal triangle has a large bounding box but few covered pixels. The algorithm tests all pixels in the box regardless. This is why triangle area relative to bounding box area matters for performance — and why games avoid very thin, long triangles (slivers).

02.04

Software vs Hardware Rendering

The rasterizer you just saw running step-by-step is a software rasterizer. It executes on the CPU, one pixel at a time, in a Python loop. This is instructive — but it is also orders of magnitude too slow for real games.

A 1920×1080 frame contains over two million pixels. A game scene might contain hundreds of triangles, each covering thousands of pixels. A CPU core processes operations sequentially — it can execute billions of operations per second, but those operations happen one after another.

Software Renderer (CPU) Hardware Renderer (GPU)
Pixel processing Sequential Massively parallel
Cores available 4–32 Thousands to tens of thousands
Programming model Arbitrary code Constrained shader programs
Memory bandwidth General RAM Dedicated VRAM (much faster)
Flexibility Very high High within pipeline structure
Frame rate at 1080p Often <1 FPS 60–240+ FPS

A software rasterizer remains useful for: understanding how rendering works at the mathematical level, platforms without GPU access, offline rendering tools, and procedural image generation. In this course, we start in software and move to hardware in Module 4.

02.05

Why GPUs Exist

The key observation behind GPUs is that computing the color of pixel (100, 200) is entirely independent of computing the color of pixel (101, 200). There is no dependency between them. Both can be computed at exactly the same time on different hardware units.

This is called data parallelism. CPUs are built to execute a single stream of instructions as quickly as possible, with complex branch prediction, caching, and out-of-order execution. GPUs trade most of that complexity for sheer number of arithmetic units — they run many simple programs simultaneously.

The Trade-off
GPU cores are much simpler than CPU cores. They cannot make independent decisions efficiently — if one thread in a group of 32 takes a different code path than the others, all 32 threads wait. This is called warp divergence, and writing GPU-friendly code means understanding it.

From a game development perspective: the rendering pipeline is structured specifically to exploit GPU parallelism. Vertices are processed in parallel, fragments are shaded in parallel. Shaders are programs that express what to do to one vertex or one pixel — the GPU runs them on all of them simultaneously.

						Exercise · Complete Software Renderer
					

					
Putting it all together: a framebuffer, a rasterizer, and PIL for display output.

					
import numpy as np
from PIL import Image

WIDTH, HEIGHT = 320, 240

def edge_fn(ax, ay, bx, by, px, py):
    return (bx - ax) * (py - ay) - (by - ay) * (px - ax)

def draw_triangle(fb, v0, v1, v2, color):
    # Compute bounding box, clipped to framebuffer
    min_x = max(0, int(min(v0[0], v1[0], v2[0])))
    max_x = min(WIDTH-1, int(max(v0[0], v1[0], v2[0])))
    min_y = max(0, int(min(v0[1], v1[1], v2[1])))
    max_y = min(HEIGHT-1, int(max(v0[1], v1[1], v2[1])))
    for y in range(min_y, max_y + 1):
        for x in range(min_x, max_x + 1):
            e0 = edge_fn(*v0, *v1, x+.5, y+.5)
            e1 = edge_fn(*v1, *v2, x+.5, y+.5)
            e2 = edge_fn(*v2, *v0, x+.5, y+.5)
            if e0 >= 0 and e1 >= 0 and e2 >= 0:
                fb[y, x] = color

# Create framebuffer and clear to dark
framebuffer = np.full((HEIGHT, WIDTH, 3), [15, 15, 25], dtype=np.uint8)

# Draw three overlapping triangles
draw_triangle(framebuffer,
    (40, 200), (160, 40), (280, 200),
    [0, 229, 200])
draw_triangle(framebuffer,
    (80, 40),  (200, 200), (310, 40),
    [255, 95, 58])

Image.fromarray(framebuffer).save("render.png")python

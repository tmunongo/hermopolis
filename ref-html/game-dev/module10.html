10.01

Scene Graphs

A scene graph organises all objects in a game as a tree. Each node has a local transform (position, rotation, scale) relative to its parent. The world transform of any node is computed by multiplying all local transforms from the root down to that node.

This hierarchy makes intuitive operations trivial: attach a sword to a character's hand, and the sword automatically inherits the hand's every movement. Move the character's root node and the entire skeleton — every attachment included — follows without any additional code. 

class Node:
    def __init__(self, name, local_transform=None):
        self.name      = name
        self.local_t   = local_transform or Transform()
        self.world_t   = Transform()    # computed each frame
        self.parent    = None
        self.children  = []
        self.components= []              # sprites, colliders, etc.

    def add_child(self, child):
        child.parent = self
        self.children.append(child)
        return child

    def update_transforms(self, parent_world=None):
        parent_world = parent_world or identity()
        self.world_t = parent_world @ self.local_t   # Module 3 matrix math
        for child in self.children:
            child.update_transforms(self.world_t)

    def render(self, renderer):
        for comp in self.components:
            comp.render(renderer, self.world_t)
        for child in self.children:
            child.render(renderer)python

Dirty Flag Optimisation
Recomputing world transforms for every node every frame is wasteful if most nodes haven't moved. The dirty flag pattern marks a node's world transform as stale only when its local transform changes. Only stale nodes (and their descendants) are recomputed. Large static scenes — rooms, terrain — benefit enormously from this.
10.02

Entity-Component-System (ECS)

ECS is an architectural pattern that separates identity (Entity), data (Component), and behaviour (System). An entity is just an integer ID. A component is a plain data struct with no methods. A system is a function that operates on all entities that have a specific set of components.

The key insight: instead of a single GameObject with many optional fields, you have a table of component data, queried by type. Systems iterate those tables rather than traversing a tree of heterogeneous objects. This makes iteration predictable, cache-friendly, and parallelisable. 

# Components — pure data, no methods
from dataclasses import dataclass, field
from typing import Dict, List, Any

@dataclass
class Position:  x: float = 0; y: float = 0

@dataclass
class Velocity:  vx: float = 0; vy: float = 0

@dataclass
class Sprite:    texture: str = ''; frame: int = 0

@dataclass
class Health:    hp: int = 100; max_hp: int = 100

# World — stores component tables indexed by entity ID
class World:
    def __init__(self):
        self._next_id   = 0
        self._components: Dict[type, Dict[int, Any]] = {}

    def create_entity(self) -> int:
        eid = self._next_id; self._next_id += 1; return eid

    def add(self, eid: int, component):
        t = type(component)
        self._components.setdefault(t, {})[eid] = component

    def get(self, eid: int, comp_type):
        return self._components.get(comp_type, {}).get(eid)

    def query(self, *comp_types):
        # Yield (eid, comp1, comp2, ...) for all entities with all types
        tables  = [self._components.get(t, {}) for t in comp_types]
        primary = min(tables, key=len)
        for eid in primary:
            comps = [t.get(eid) for t in tables]
            if all(c is not None for c in comps):
                yield (eid, *comps)

# Systems — pure functions that transform components
def movement_system(world: World, dt: float):
    for eid, pos, vel in world.query(Position, Velocity):
        pos.x += vel.vx * dt
        pos.y += vel.vy * dt

def render_system(world: World, renderer):
    for eid, pos, spr in world.query(Position, Sprite):
        renderer.draw_sprite(spr.texture, pos.x, pos.y, spr.frame)python

10.03

Scene Graph vs ECS: When to Use Which

These are not competing ideals — they solve different problems. Many modern engines combine them: a scene graph organises spatial hierarchy and editor-friendly object relationships, while ECS handles gameplay logic and high-volume simulation. Understanding the trade-offs lets you choose appropriately.

Property Scene Graph ECS
Mental model Objects in a hierarchy Data tables + functions
Transform inheritance Built-in, natural Requires explicit parent component
Adding behaviour Subclass or attach component Add a component, write a system
Cache performance Object fields scattered in RAM Component arrays are contiguous
1000+ entities Slower — traverses full tree Fast — tight loops over arrays
Editor tooling Natural tree view Requires special tooling
Best for 2D games, jam projects, UI Simulations, large worlds, bullets
Examples Godot (default), Unity (legacy) Unity DOTS, Bevy, Flecs
For This Course
Our mini-engine uses a hybrid: a scene graph for spatial organisation (from Module 3), with each node carrying a flat list of components. Systems iterate nodes that have a specific component type. This is the pattern used by Godot, Unity's MonoBehaviour model, and most indie engines — simple enough to reason about, capable enough for a full 2D game.

Update Order and Subsystems

The order in which engine subsystems run each frame is not arbitrary. A wrong order introduces one-frame latency, physics-render desync, or use-after-destroy crashes. Each subsystem reads outputs from previous ones and must complete before the next one begins.

Destroy-on-Frame-End
Never destroy (remove) entities immediately when requested during the update step. Code later in the same frame may still hold a reference and try to read from the destroyed object. Queue all destruction requests and process them at End Frame, after all systems have finished. This single pattern eliminates an entire class of use-after-free bugs. 
class Engine:
    def run_frame(self):
        # 1–2: Time + input
        dt = self.measure_dt()
        self.input.begin_frame()
        self.process_events()

        # 3: Pre-update (game scripts)
        for system in self.pre_update_systems:
            system.update(self.world, dt, self.input)

        # 4: Physics (fixed or variable)
        self.physics.step(self.world, dt)

        # 5: Post-update (cameras, animations)
        for system in self.post_update_systems:
            system.update(self.world, dt)

        # 6: Update scene graph transforms
        self.scene_root.update_transforms()

        # 7: Render
        self.renderer.render_frame(self.world, self.camera)

        # 8: Deferred cleanup
        self.world.flush_destroyed()python
10.05

Resource Loading and Memory

A resource manager centralises asset loading, caches assets to prevent duplicate GPU uploads, and tracks memory usage. Every texture, audio clip, and shader should pass through the resource manager — never loaded inline in game logic. 

class ResourceManager:
    def __init__(self, ctx, base_path='assets/'):
        self.ctx       = ctx
        self.base_path = base_path
        self._cache    = {}          # path → loaded resource
        self._pending  = []          # async load queue

    def load_texture(self, path: str):
        if path in self._cache:
            return self._cache[path]   # cached — no GPU upload needed

        from PIL import Image
        img = Image.open(self.base_path + path).convert('RGBA')
        img = img.transpose(Image.FLIP_TOP_BOTTOM)
        tex = self.ctx.texture(img.size, 4, img.tobytes())
        tex.filter = (moderngl.NEAREST, moderngl.NEAREST)
        self._cache[path] = tex
        return tex

    def unload(self, path: str):
        if path in self._cache:
            self._cache[path].release()   # free GPU memory
            del self._cache[path]

    def memory_stats(self):
        return {'loaded': len(self._cache),
                'paths':  list(self._cache.keys())}python

Scene Manager

A scene manager handles transitions between states — menus, gameplay, cutscenes. Each scene defines its own init, update, and teardown. The manager ensures clean transitions: old resources released, new ones loaded. 

class SceneManager:
    def __init__(self):
        self._scenes  = {}     # name → scene class
        self._current = None
        self._pending = None  # change requested this frame

    def register(self, name, scene_class):
        self._scenes[name] = scene_class

    def go_to(self, name, **kwargs):
        self._pending = (name, kwargs)   # defer to end of frame

    def end_frame_transition(self, resources):
        if self._pending is None: return
        name, kwargs = self._pending;  self._pending = None

        if self._current:
            self._current.on_exit(resources)   # teardown current

        self._current = self._scenes[name](**kwargs)
        self._current.on_enter(resources)     # setup new scene

    def update(self, dt, inp):
        if self._current: self._current.update(dt, inp)python
